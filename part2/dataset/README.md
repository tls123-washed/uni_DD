# Campus Threads · Part 2

**Синтетический датасет.** Период с 1 сентября по 23 ноября 2026 года включительно. Время во всех CSV указано по Алматы, UTC+05:00. Данные созданы по модели Campus Threads для демонстрации дашборда. В них 600 вымышленных аккаунтов, 18 сообществ, 32 мероприятия и 1 056 бесплатных пропусков. Графики описывают эту симуляцию. В рабочую базу данные не загружались.

## Google Colab

1. Открой [Google Colab](https://colab.research.google.com/). Выбери **File → Upload notebook** и загрузи `Campus_Threads_Part2.ipynb`.
2. Нажми **Runtime → Run all**. По запросу первой ячейки выбери файл `campus_threads_dataset.zip`. Распаковывать его для Colab не нужно.
3. В последней ячейке выбери факультет, даты и категорию мероприятий. Если графики не обновились, запусти эту ячейку кнопкой ▶. У графиков Plotly есть всплывающие подсказки. В обычном Jupyter значения можно менять в коде последней ячейки.

Код каждой визуализации находится в отдельной ячейке. `Campus_Threads_Dashboard.html` можно открыть локально в браузере для показа всех пяти графиков. HTML сохраняет подсказки, легенды и масштабирование. Общие фильтры находятся в ноутбуке.

## Tableau или Power BI

Распакуй `campus_threads_dataset.zip`. Готовые таблицы из папки `bi` читаются отдельно и подходят для быстрого импорта через подключение к текстовому файлу. CSV используют UTF-8 и запятую как разделитель. Поля с датами и временем следует импортировать как даты или метки времени, вместимость и количество как целые числа, `fill_pct` как число от 0 до 100.

| Визуализация | CSV | Поля и расчёт |
| --- | --- | --- |
| Регистрации и активные пользователи по неделям | `bi/activity.csv` | Неделя по `date` с понедельника. Регистрации — строки `action = register`. Активные — уникальные `user_id` среди действий, отличных от регистрации, с непустым ID. |
| Размер сообществ | `bi/communities.csv` | `name` и `members` на конец периода. `threads`, `replies` и `likes` доступны для подсказки. |
| Заполняемость мероприятий | `bi/events.csv` | Точка на каждое событие. `capacity` на X, `fill_pct` на Y, цвет по `category`, `tickets_issued` в подсказке. |
| Когда пользователи активны | `bi/activity.csv` | `weekday` по Y, `hour` по X, количество строк с непустым `user_id` в цвете. 1 — понедельник, 7 — воскресенье. |
| Использование функций | `bi/activity.csv` | `action_group` и количество строк. Для сравнения действий студентов исключи пустой `user_id`. |

`bi/communities.csv` и `bi/events.csv` уже агрегированы. Для фильтра сообществ по факультету свяжи `tables/community_members.csv` с `tables/users.csv` по `user_id` и с `tables/communities.csv` по `community_id`. Не соединяй вместе лайки, билеты и подписки по `user_id` ради подсчётов. Несколько записей в каждой таблице размножат строки в результате.

## Таблицы и связи

| CSV в `tables` | Одна строка | Связи и поля |
| --- | --- | --- |
| `faculties.csv` | Факультет | `faculty_id`, `faculty_code`, `faculty_name`. Справочник по схеме проекта. |
| `users.csv` | Студенческий профиль | `user_id`, `username`, `faculty_id`, `year_of_study`, `registered_at`, `bio`, признаки `site_moderator`, `event_organizer`. |
| `communities.csv` | Сообщество | `community_id`, `name`, `category`, `created_at`, `creator_id → users`. Категория и создатель добавлены для аналитики в симуляции. |
| `community_members.csv` | Действующее членство | `community_id → communities`, `user_id → users`, `role` (`member`, `moderator`, `admin`), `joined_at`. |
| `posts.csv` | Тред или ответ | `post_id`, `author_id → users`, `community_id → communities`, `parent_post_id → posts`, `is_anonymous`, `created_at`, `content`, `deleted_at`. Пустой `parent_post_id` означает тред, пустой `community_id` — общую ленту. `deleted_at` есть только в симуляции. |
| `post_hashtags.csv` | Хэштег публикации | `post_id → posts`, `tag`. Объединяет две таблицы приложения `hashtags` и `post_hashtags`. |
| `likes.csv` | Действующий лайк | `user_id → users`, `post_id → posts`, `liked_at`. |
| `follows.csv` | Действующая подписка | `follower_id → users`, `followee_id → users`, `followed_at`. |
| `events.csv` | Мероприятие | `event_id`, `title`, `category`, `organizer_id → users`, `organizer_role`, `published_at`, `starts_at`, `venue`, `capacity`, `price_kzt`. Категория, дата публикации и цена добавлены в выгрузку для аналитики. Цена всех пропусков равна нулю. |
| `event_tickets.csv` | Выданный пропуск | `ticket_id`, `event_id → events`, `user_id → users`, `issued_at`. Один пропуск на человека для каждого события. |
| `activity_log.csv` | Смоделированное действие | `activity_id`, `occurred_at`, `user_id → users`, `action`, `action_group`, `target_type`, `target_id`, необязательные `community_id` и `event_id`, `origin`. Пустой `user_id` — действие оператора БД по выдаче или снятию роли. |

`data_source = synthetic` означает, что строка относится к набору для демонстрации. `origin = modeled_record` означает действие, представленное обычной записью в модели приложения. `origin = modeled_usage` обозначает симуляцию истории действий, например поиск, просмотры, удаление, отмену лайка, выход из аккаунта и переключение темы. Текущая PostgreSQL не хранит такую историю целиком. Членства, лайки и подписки показывают конечное состояние, поэтому их число может отличаться от числа соответствующих действий. Все даты и результаты в наборе сгенерированы. Словарь категорий действий приведён в `action_dictionary.csv`.

У анонимных публикаций в этом учебном наборе есть вымышленные `author_id` для группировки. В отчёте о реальных данных такие идентификаторы публиковать не требуется. Выданный билет показывает запись на событие. Для посещаемости потребовалась бы отдельная отметка о проходе.

## Как смотреть реальные цифры

Открой Neon → **KBTU-threads → SQL Editor → production → neondb**. Выполни нужный запрос из `real_stats_readonly.sql`. Он возвращает сводки по регистрациям, сообществам, публикациям и пропускам. Если интерфейс предлагает выгрузку результата, скачай таблицу. В pgAdmin тот же запрос можно выполнить в **Query Tool** подключённой Neon и сохранить результат через **Save results to file**.

Для визуализаций из реальной базы используй агрегаты. Историческую активность по часам можно построить по датам постов, лайков, подписок и выдачи билетов. Просмотры и поиск из текущей схемы достать нельзя, потому что для них не настроен журнал. Синтетические и наблюдавшиеся данные обозначай раздельно.
